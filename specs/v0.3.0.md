# Scribae v0.3.0

## Summary

Active spec. Covers work landed since the 0.2.0 release plus the hardening needed to cut
0.3.0: the translation backend moved off the removed `transformers` pipeline task onto
direct seq2seq models, translation input handling stopped silently truncating and is now
memory-bounded, note front matter is validated more strictly, and the dependency floor was
raised (typer 0.27, mypy 2.3, python-frontmatter 1.3). What remains is release hygiene and
closing the coverage gaps those changes opened.

## Goals

- Ship a correct, memory-bounded translation path on the seq2seq backend.
- Keep the repository releasable: changelog, version, and docs matching the code.
- Keep the checks green under the pinned toolchain (ruff, mypy strict, pytest).

## Potential Features

### Translation Backend Migration

`transformers` removed the `translation` pipeline task; `translate/mt.py` now drives
seq2seq models directly. The `transformers` seam is typed and test doubles are shared via
`tests/mt_fakes.py`.

### Translation Input Safety

Input is no longer silently truncated, and batch size is bounded so long documents cannot
grow memory without limit. Segment/batch boundaries need explicit regression coverage.

### Note Front Matter Validation

A note title must be a string in front matter; non-string titles fail with a clear error
instead of propagating into prompts.

### Release Hygiene

`CHANGELOG.md` has no Unreleased section, so post-0.2.0 commits are undocumented, and
`pyproject.toml` still reads `0.2.0`. Cutting 0.3.0 means reconciling changelog, version,
and README/AGENTS docs.

## Caution

- The real-model path stays untested by default. Any seq2seq change needs a run with
  `SCRIBAE_REAL_MODEL_TESTS=1`, not just the stubbed unit suite.
- Batch bounding and truncation interact: a fix on one side can silently re-break the other.
- Dependency bumps (typer, mypy) have already forced source changes; treat bumps as behavior
  changes, not chores.

## Recommendation About LLM Support

Unchanged from v0.2.0: one OpenAI-compatible seam, async calls with timeout and retries,
no provider-specific SDKs. The translation post-edit pass keeps using that same seam.

## Explicitly Excluded

- New pipeline commands.
- GPU/accelerator builds of PyTorch.
- Any hosted service surface.
